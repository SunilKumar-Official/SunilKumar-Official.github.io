Business problem

Raw support-chat conversations arrive one API call at a time, in a source-specific shape that changes meaning depending on who's asking — reporting, workforce planning, and future analysis all need the same clean, structural view of "what happened in this conversation," and none of them should have to re-derive it from the raw API format every time.

My contribution

I designed, built, and personally administer the data platform this pipeline runs on — not just the pipeline itself, but the underlying infrastructure (orchestration, storage, access control) my team uses to build and run data work on. Within that platform, I designed and built this specific three-stage pipeline end to end, including finding and fixing two separate real production problems after it went live (detailed below).

Data & tools

Dagster (orchestration), Python, Postgres, and the Zoho SalesIQ chat API, inside a self-designed data platform (a shared internal Python package providing storage, validation, and configuration primitives; Postgres and a local LLM runtime available to every project built on it).

Scope & scale

180,000+ support conversations processed through the pipeline. Three independently scheduled stages, each a full project in its own right: extraction, a canonical normalization layer, and an enrichment layer producing ten relational tables (conversation facts, message facts, timing/turn-taking facts, and rollup metrics) ready for direct querying by dashboards and future analysis.

Approach

I designed this as three independent stages, each reading the one before it only through a stable, read-only contract (a database table or a file layout) — never by importing another stage's code — so each stage can be rebuilt, rescheduled, or fixed without the others needing to change:

  1. Extraction pulls raw transcripts from the Zoho API and tracks per-conversation status in a database catalog.
  2. Canonical parses that raw, source-specific shape into one stable, typed structure per conversation — built once, fully rebuildable from the raw data at any time, so it's never a second source of truth.
  3. Enrichment turns each canonical conversation into ten relational database tables — conversation-level facts, per-message facts, turn-taking and timing, handoffs between bot and human agents, abandonment detection, and rollup metrics — so downstream reporting can query directly with SQL instead of re-parsing conversation structure every time.

After it went live, I found and fixed two separate real problems, not hypothetical ones:

  • A reliability gap. A five-day extraction outage went unnoticed because failure alerts were being sent but not escalated. I designed and built a watchdog that runs a handful of independent health checks daily and keeps escalating until someone acts — plus a real performance fix, replacing a full-table rewrite on every run with a targeted update once the status table grew large.
  • A silent coverage gap. I discovered the live pipeline had only ever been extracting two of six real conversation departments and one of several statuses — thousands of conversations (including an entire WhatsApp channel) had never been captured, with no error raised anywhere, because the original filter was never revisited as the business grew. Fixing it surfaced a genuine data-correctness problem along the way: the chat platform reuses the same conversation identifier across separate WhatsApp contacts with the same customer, so a returning customer's new messages were silently landing inside a conversation record the pipeline already considered "done." I designed a cost-aware fix — a cheap status check for the normal case, and a full refresh only for the much smaller WhatsApp volume where that's actually necessary — rather than re-checking everything the same way regardless of cost.

Outcome

A reliable, fully monitored pipeline that now captures every real conversation channel and status, not just the ones originally configured — closing a gap that had existed silently for months. The extraction window is self-healing by design, and the alerting now escalates until a real person acts on it, instead of a failure going unnoticed for days.

Evidence

Not yet public — no sanitized repository exists for this project yet (a planned follow-up, not available for this round).

Limitations & what's next

The root cause of one earlier logging gap (a few days with no recorded pipeline runs) is still unconfirmed, though the new monitoring makes a recurrence immediately visible even without knowing the original cause. Backfilling the conversations missed during the multi-month coverage gap is a planned follow-up, separate from the fix itself.
